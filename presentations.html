Project overview

Four workshops, one codebase

DigiBank is a fictional digital banking application built across four progressive DevSecOps workshops. Each one adds a new layer of security analysis to the same codebase, following the "Shift Left" philosophy — moving security earlier and earlier in the software lifecycle.

Lab 2 — Remediations implemented
Secrets in configuration — database credentials moved to environment variables; no committed default password; SQL/error detail exposure disabled.
Input validation — bounded Unicode‑letter format for names; bounded alphanumeric pattern for identity numbers.
Data minimization — customer responses omit the sensitive identity number.
Error handling — GlobalExceptionHandler returns generic messages; no stack traces or internal details leaked.
Business rules in services — transfer validation repeated at the service layer; positive amount and non‑negative balance enforced.
Dependency updates — versions pinned and reviewed; unavoidable CVEs documented in a time‑bounded suppressions file.
Test strengthening — focused tests for malformed input, rejection branches, and generic errors — improving the PITest mutation score.

Lab 4 — Remediations implemented
Overly large image — multi‑stage Dockerfile: a build stage produces the jar, a slim runtime stage copies only the runnable artifact. Image reduced to 254 MB from 754 MB.
Container running as root — added a non‑root user; the app now runs as an unprivileged uid, verified at build time.
Secrets in containerized config — credentials injected via environment variables; .dockerignore excludes .env, logs, and local reports.
Swagger exposure — OpenAPI disabled by default, enabled only under dev/test profiles; disabled in prod and ci.
No automated checking — added OWASP Dependency‑Check (CVSS ≥ 7 gate) and Trivy image scanning to a dedicated pipeline.

Additional challenges

Beyond the per‑lab hurdles

Cross‑cutting challenges we faced while industrializing security across all four labs.

Tool sprawl
Many scanners, each with its own config, reports, and false positives to manage.
False‑positive triage
Tuning suppressions without accidentally hiding real issues.
CI runtime & cost
Many scans on every push lengthen the pipeline and consume minutes.
Velocity vs. security
Keeping the pipeline green while adding new security gates.
Environment parity
Local vs. CI differences — e.g. SonarQube on localhost unreachable from a runner.
NVD rate limits
Dependency‑Check needs an API key to keep the NVD download fast.

Lessons learned

What the four labs taught us

Security is layered and continuous — Shift Left works.
A clean, testable base makes later hardening far easier.
SAST + DAST complement each other — static finds code issues, dynamic confirms runtime exposure.
Suppressions must be time‑bounded and documented, never permanent.
Automation is essential — CI gates enforce discipline; manual scanning doesn't scale.
No secrets in code — use environment variables and secret managers.
False positives are part of the job — triage and justify them.
A modular monolith balances clean architecture with operational simplicity.
Reproducible evidence (reports, collections, scripts) is essential for review.
Balance security with developer velocity.
Security is a team responsibility, not a single role.
Conclusion

Security as a continuous property

Across the four labs, DigiBank progressed from a clean, testable modular monolith to a system whose source code, runtime behavior, and supply chain are all analyzed, hardened, and automated — the full DevSecOps / Shift Left philosophy in practice.

A secure application is not just well‑written code. It is code that is statically and dynamically validated, built from trusted dependencies, shipped in a hardened container, and continuously re‑checked by an automated pipeline.
